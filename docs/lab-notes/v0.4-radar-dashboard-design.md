# v0.4 Radar Candidate Dashboard Design

Date: 2026-06-03

## Goal

Prepare a future `/radar` view in the existing Local Model Performance Dashboard
without building it before candidate and benchmark data stabilizes.

## Proposed Shape

Add a Radar Candidates page to `apps/model-dashboard` that reads normalized
candidate records from `data/model_registry` or a future radar import artifact.
The page should stay local-first, dependency-free, and separate candidate claims
from benchmark scores.

## Candidate View

Show a compact table with:

- Candidate name.
- Model family.
- Provider or org.
- Format or runtime.
- Candidate status: `watchlist`, `ready_for_eval`, `skip`, or
  `needs_more_info`.
- Why interesting.
- Risk notes.
- Proposed eval.
- Source packet/report link.

Filters should include:

- Status.
- Model family.
- Runtime or format.
- Risk flag.
- Ready-for-eval only.

## Linkage

The view should link across the existing local workflow:

```text
Radar candidate
  -> approved source packet
  -> radar report
  -> benchmark artifact directory
  -> dashboard model/run after CSV import
```

Candidate records must not become `eval_scores` rows. Only completed local
benchmark runs with scored evidence should feed dashboard scores and final
labels.

## Constraints

- No new runtime dependencies for v0.4 unless separately approved.
- No web fetching, cloud APIs, model downloads, or secrets.
- Candidate-only records should remain visually distinct from evaluated models.
- The first implementation should extend the existing dashboard instead of
creating a second app.

## Readiness Criteria

Build this page after at least one real local candidate has both:

- a radar source packet/report; and
- a successful or failed benchmark artifact linked to dashboard import files.
